The filter-scale sweep costs what we measured, not what the algorithm suggested

Splitting a 30-scale sweep across PBS jobs needs a cost model to balance the batches. The obvious one — Gaussian filtering is an O(L·σ) correlation with σ ∝ ℓ, so weight by ℓ — was wrong by an order of magnitude. Three runs, at 256², 512² and 1024², replaced it with an affine model whose shape holds everywhere and whose magnitude does not extrapolate. The corrected split turned 43.2 h of sequential work at 1024² into 5.7 h.

the refutation

Eight batches that should have taken equal time didn't

The split is cost-weighted, so a correctly-weighted run produces batches of equal wall time by construction. That makes any real run a direct test of the weighting. The first one failed it.

the correction

A large fixed cost per scale swamps the ℓ term at small ℓ

Per-scale cost is affine, not proportional. Loading and rechunking ds_filt, writing the checkpoint, and the sort's downstream use are all fixed-size work that doesn't care how wide the filter kernel is — and across a log-spaced sweep spanning 51× in ℓ, that fixed term dominates most of the range.

cost per scale  =  3.69 min  +  0.081 min · (ℓ / Δx) fitted at 256², Δx = 3.906 km, 64 levels, 41 timesteps

Both terms scale with data volume Nx·Ny·Nz·n_times, but only the second carries a 1/Δx, so the two diverge with resolution. Storing the weight resolution-free as w ∝ 1 + 0.0215·(ℓ/Δx) — a fixed cost plus a term proportional to kernel width in grid cells — keeps it valid at any grid. A kernel about 47 cells wide doubles the per-scale cost. The three runs independently imply 0.0221, 0.0239 and 0.0203, a 16% spread with no trend across a 16× grid range; 0.0215 is the largest value that still lets the split reach its floor at all three.

the validation

Fit at 256², predict 512², check

A model fitted and evaluated on the same run proves nothing. Each larger run is a genuine held-out test: take the previous resolution's coefficients, scale both by the data-volume ratio, and predict every batch before looking at it. Doing that twice is what separates a model that works from one that only looked like it did.

So the honest split is: the affine shape holds at every resolution (each run fits to a few percent), and the weight ratio B/A is stable across a 16× grid range — 0.0221, 0.0239, 0.0203, no trend. That ratio is all the batch balancing depends on, which is why the split works. What does not hold is cost ∝ data volume. 256²→512² landed slightly under it (−11% fixed, −4% σ) and read as confirmation; 512²→1024² landed well over (+34% and +14%).

An earlier note in CLAUDE.md claimed per-scale cost blows up ~2.5× faster than O(L·σ) reasoning predicts. On two points I called that refuted. With three, it is better described as wrong in magnitude but right in direction — there is a real super-volume trend of roughly +20% per 4× grid jump. Use the model to balance batches against each other; add that margin when using it to predict absolute runtime at a resolution nobody has run yet.

the payoff

At 1024², memory binds before walltime does

The run happened: 1024×1024×64, 30 scales, 19 timesteps, N_SCALE_JOBS=10. Sequential work of 43.2 h finished in 5.7 h, with 258 GiB per scale and a heaviest batch of 441 GiB — inside both the 23:59 cap and the 682 GiB request, with room. Cost and memory are both linear in n_times, and they reach their ceilings at different points. Batch size moves walltime only — peak memory is set by one scale's working set, so no N_SCALE_JOBS value rescues an over-budget run.

What to run

# 1024², keep the time axis at or below ~40. Run the sweep as its own step:
# SWEEP=1 splits at submit time, before the simulation .nc exists to weight against.
cd postprocessing
bash submit_sweep.sh NX=1024 NY=1024 NZ=64 N_SCALES=30 N_SCALE_JOBS=10 N_TIME_SKIP=2

N_SCALE_JOBS=10 is the threshold below which the split can't reach its own floor. Two bounds apply to the heaviest batch — an even share, and the single costliest scale, which is indivisible. Under K = total/max(cost) (10 at 1024², 14 at 512², 19 at 256²) the even share binds, and contiguous ranges over log-spaced scales land 16–22% above it; an oracle splitter handed the exact costs does no better, so that gap is partition granularity, not a weighting error. Above it the costliest scale binds and the split is exact. Raising K is the fix, not a cleverer partition. The threshold is found by partitioning at each candidate K, not from total/max(cost) — that bound is where the floor stops improving, one to four jobs short of where a contiguous split attains it. The earlier K=8 advice sat below it everywhere: +20% at 1024², +65% at 512². If the time axis can't come down, the remaining lever is an FFT-based Gaussian filter — O(L log L), independent of σ — which removes ℓ from the cost model rather than redistributing it.

Fits: least squares on per-batch wall time from three real PBS fan-outs — 256×256×64 / 41 timesteps / 8 jobs, 512×512×65 / 21 / 8, and 1024×1024×64 / 19 / 10 — over 30 log-spaced filter scales from 2Δx to 0.4·Lx. Memory figures are the anonymous baseline; PBS resources_used.mem also counts reclaimable page cache from the per-scale checkpoints, which is why a 16-scale batch reports ~200 GiB while its real working set is that of one scale.
