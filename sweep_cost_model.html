The filter-scale sweep costs what we measured, not what the algorithm suggested

Splitting a 30-scale sweep across PBS jobs needs a cost model to balance the batches. The obvious one — Gaussian filtering is an O(L·σ) correlation with σ ∝ ℓ, so weight by ℓ — was wrong by an order of magnitude. Two runs at 256² and 512² replaced it with an affine model that predicts out of sample to 7%, and moved the binding constraint at 1024² from walltime to memory.

assumed cost ratio51× largest scale vs. smallest, weighting by ℓ
measured at 256²3.2× what the affine fit gives instead
out-of-sample error7.4% 256² fit predicting eight 512² batches
1024² hard limit57 timesteps before a single scale exceeds the memory request

the refutation

Eight batches that should have taken equal time didn't

The split is cost-weighted, so a correctly-weighted run produces batches of equal wall time by construction. That makes any real run a direct test of the weighting. The first one failed it.

spread 7.8× — should be 1.0×

the correction

A large fixed cost per scale swamps the ℓ term at small ℓ

Per-scale cost is affine, not proportional. Loading and rechunking ds_filt, writing the checkpoint, and the sort's downstream use are all fixed-size work that doesn't care how wide the filter kernel is — and across a log-spaced sweep spanning 51× in ℓ, that fixed term dominates most of the range.

cost per scale  =  3.69 min  +  0.081 min · (ℓ / Δx) fitted at 256², Δx = 3.906 km, 64 levels, 41 timesteps

Both terms scale with data volume Nx·Ny·Nz·n_times, but only the second carries a 1/Δx, so the two diverge with resolution. Storing the weight resolution-free as w ∝ 1 + 0.0230·(ℓ/Δx) — a fixed cost plus a term proportional to kernel width in grid cells — keeps it valid at any grid. A kernel about 43 cells wide doubles the per-scale cost. The two runs independently imply 0.0221 and 0.0239 across a 2.08× change in data volume, which is the check that the resolution-free form holds.

the validation

Fit at 256², predict 512², check

A model fitted and evaluated on the same run proves nothing. The 512² run is a genuine held-out test: take the 256² coefficients, scale both by the data-volume ratio (2.081), and predict all eight batches before looking at them.

This specifically retires an earlier worry in CLAUDE.md that per-scale cost blows up ~2.5× faster than O(L·σ) reasoning predicts. It doesn't. That anecdote compared two runs differing in n_times as well as grid — and n_times turns out to be a first-order term in its own right.

the payoff

At 1024², memory binds before walltime does

Cost and memory are both linear in n_times, and they hit their respective ceilings at different points. Batch size moves walltime only — peak memory is set by one scale's working set, so no N_SCALE_JOBS value rescues an over-budget run.

What to run

# 1024², keep the time axis at or below ~41
cd postprocessing
bash submit_sweep.sh NX=1024 NY=1024 NZ=64 N_SCALES=30 N_SCALE_JOBS=12 N_TIME_SKIP=2

N_SCALE_JOBS=12 clears the threshold below which the split can't reach its own floor. Two bounds apply to the heaviest batch — an even share, and the single costliest scale, which is indivisible. Under K = total/max(cost) (9 at 1024², 11 at 512², 15 at 256²) the even share binds, and contiguous ranges over log-spaced scales land 20–26% above it; an oracle splitter handed the exact costs does no better, so that gap is partition granularity, not a weighting error. Above it the costliest scale binds and the existing split is exact. Raising K is the fix, not a cleverer partition. The earlier K=8 advice sat below the threshold at every resolution. If the time axis can't come down, the remaining lever is an FFT-based Gaussian filter — O(L log L), independent of σ — which removes ℓ from the cost model rather than redistributing it.

Fits: least squares on per-batch wall time, two runs of 8 PBS batch jobs each (256×256×64 / 41 timesteps, 512×512×65 / 21 timesteps), 30 log-spaced filter scales from 2Δx to 0.4·Lx. Memory figures are the anonymous baseline; PBS resources_used.mem also counts reclaimable page cache from the per-scale checkpoints, which is why a 16-scale batch reports ~200 GiB while its real working set is that of one scale.
